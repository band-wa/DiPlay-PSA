# Fork 维护策略(上游变更取舍规则)

> 目的:明确本 fork(`band-wa/DiPlay-PSA`)与上游(`shihabal3amri/DiPlay`)的关系,以及后续版本变更的准入标准。
> 基线:本 fork 面向标致/雪铁龙(PSA)安卓 9 车机,已整体移除 BYD/DiLink 集成(见 [BYD_REMOVAL_AUDIT.md](BYD_REMOVAL_AUDIT.md))。
> 结论:**以本 fork 自身为基线,不做上游整包合并**;上游代码只在"必要补丁"的窄范围内选择性引入。
> 适用:所有后续维护。分析上游 commit 时,先按本文规则筛出候选,再交车机实测方审核决定。

## 1. 为什么不做整包合并

- 上游主线持续朝 BYD/DiLink 方向加深(仪表盘、HUD、方向盘、车辆数据等)。`git merge` 会把本 fork 已删除的代码与资源带回来,并制造长期冲突面。
- 上游新特性常依赖本 fork 不存在的基础设施。例如:
  - Same LAN("既有 Wi-Fi")模式的**双栈多地址监听**(`AirPlayPortSelector.bindAll`、`AirPlayAttachment.additionalAddresses`)——引入后必须立刻拆掉;
  - **BYD 本地 ADB 自动开热点**(`CarHotspotTethering`、`CarHotspotSettings`)——本 fork 已无该子系统。
  这类"搬进来 100 行、再删掉 30 行"的改动净成本为正。
- 目标环境固定(PSA 安卓 9 车机)。无法验证的上游改动等于把未知风险带上车。
- 本地已经做了大量定制(仅本地离线认证、R8 + `-dontobfuscate`、会话内设置菜单、画面调节、准备页适配、多窗口适配),这些与上游实现方式不同,整包合并必然反复冲突。

## 2. 默认规则

1. **默认冻结**:本 fork 当前版本即基线,任何改动都需要理由。
2. 引入上游代码**只允许 `git cherry-pick -x <sha>`**(`-x` 保留来源 sha);**禁止 `git merge upstream/*`**,也禁止把上游分支直接拉成基线。
3. 需要上游尚未修复的问题时,**优先自己写一个小的本地实现**,而不是把上游那块耦合代码整体搬进来。

## 3. 允许引入的上游补丁(白名单)

| 类别 | 判据 | 本 fork 已引入的例子 |
| --- | --- | --- |
| 确认缺陷修复 | 能复现,或机制清晰且命中我们**实际使用**的路径 | `a3d988f` 诊断报告回退 Android/data(顺带解锁 Windows 测试)、`55b3069` StartSession 后无 AirPlay TCP 的看门狗与退避重试、`2193271` 车载热点接口就绪等待 |
| 有依据的性能提升 | 有测量数据,或机制明确、开销可忽略 | 暂无(方向:解码/传输/布局相关) |
| iOS/协议兼容修复 | Apple 侧变更导致握手或 AirPlay 破坏,我们无法自行实现 | 暂无(见第 6 节协议层归属) |
| 小而自包含的修正 | 单文件或单资源、零耦合、可单独回退 | `b28d68f` 简体中文文案错字、`b323b8f` USB 过滤匹配 Apple 设备、`dc22e94` 播放中保留封面并显示占位图 |

## 4. 默认跳过的上游内容(黑名单)

- **新功能与新连接模式**(如 Same LAN"既有 Wi-Fi"、分辨率范围改动等行为变更)。
- **任何 BYD / DiLink / 仪表盘集群 / HUD / 方向盘 / 车辆数据 / 本地 ADB 相关**内容。
- **构建变体与发版配置**(例如把 mobile 构建成 DiLink 4.0 变体)——与本 fork 的 release 配置直接冲突。
- **文档、官网、release-notes、下载页刷新**。
- **纯重构、日志措辞调整、内部评审文件**。

## 5. 准入验收清单(引入前必须全部通过)

1. **不恢复已删子系统**:不得要求把已移除的 BYD/仪表/HUD/ADB 代码或已跳过的特性基础设施搬回来。需要 → 跳过,或照思路自己实现。
2. **冲突可在一个提交内解决**,且解决方式写明(丢弃哪一侧、为什么)。
3. **测试全绿**:`./gradlew :shared:testDebugUnitTest :common:testDebugUnitTest`,Windows 上也不得跳过(`skipped` 必须为 0)。
4. **能上车的必须上车验证**;不能验证的,在提交信息与 CHANGELOG 中显式标注"未验证"及原因。
5. **`CHANGELOG.md` 的 fork 段写一条"为什么值得要"**,不能只写"合并上游"。
6. **保持独立可回退**:每个 cherry-pick 各自一个提交,出问题时 `git revert <sha>` 即可干净撤下。

## 6. 文件归属:紧跟上游 vs fork 自有

| 归属 | 路径 | 策略 |
| --- | --- | --- |
| **紧跟上游(协议核心)** | `shared/src/main/java/com/shilapi/xcertplay/{iap2,airplay,mfi,transport}/` | Apple 侧协议是我们唯一无法自行实现的资产,值得小步快跟;引入仍按第 3/5 节判据 |
| **fork 自有(本地优化)** | `common/`(界面、设置、资源)、`mobile/`、`automotive/`、构建配置、`docs/`、`README.md` | 只做本地改进,不随上游漂移 |

协议层是最大的长期风险来源(iOS 新版本可能改变 MFi/AirPlay 握手)。该范围内的补丁即使偏大,也应优先考虑引入并尽快实机验证。

## 7. 上游观察方式(只读)

- `git fetch upstream --tags --prune`,阅读 release notes、`CHANGELOG.md` 与关键 commit message,**不合并分支**。
- 频率:每次发版前,或每季度一次即可。
- 每次筛查的结论(引入清单 + 跳过清单及理由)在 `CHANGELOG.md` 的 fork 段留痕。最近的两次:
  - `53a3764..e6e7cc0`:仅引入上游对我们 PR #196 的合并结果(含维护者的 `if (!menuOpen)` 修正)。
  - `e6e7cc0..2fc876e`(86 个 commit):只引入 6 个必要补丁(热点就绪、无线重试、诊断回退、USB 过滤、封面占位、简中文案),其余全部跳过;其中 2 个无线补丁在模拟器上无法验证,已标注"留待上车"。

## 8. 例外

若某上游大改动修复的正是我们亲眼看到的故障,允许打破"小而自包含"的要求,但必须:

1. 先在上游源码或本 fork 上复现该故障;
2. 单独提交,便于回退;
3. 在 CHANGELOG 与提交信息中写清"未验证项"与回退方式。
